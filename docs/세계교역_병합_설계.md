# 세계 교역(v106) 병합 설계 (2026-10-19, Sonnet 초안, 미병합)

목적: 복구한 세계 확장 작업(`recovered/world-expansion`, 끊어진 커밋 `f67224a`)을 master와 합치는 방법을 정한다. **html은 건드리지 않는다**(CLAUDE.md: 빌드는 사용자가 "빌드하자"고 한 뒤에만).
정독 범위: `세계교역_설계.md`·`세계확장_진행표.md` 전부, `상거래_2단계_설계.md` 4-1~6절. 나머지 설계 문서(`선박`·`군비등급`·`기술발전`·`교역_전투반영`)는 제목·진행 상황 문장만 grep으로 봤고 **본문은 정독하지 않았다**(미확인).

## 2. 가상 병합 시험 (작업 폴더 변경 없음)
`git merge-tree --write-tree master recovered/world-expansion` 결과:
- **html 충돌 없음**: master의 `samguk_v105.html`은 분기점 `d069af4` 이후 바뀐 적이 없고(master의 24커밋은 문서·`tools/`뿐), v106은 그 위에서 이름을 바꾸고 고쳤다.
- **충돌 2개, 모두 문서**: `docs/코드지도.md`(양쪽에서 새로 만든 add/add), `docs/전투_설계_v4.md`(양쪽이 수정).
- 부수 영향(충돌은 아니지만 깨짐): master에만 있는 도구 — `lv_*_sim.js`·`battle_capture.js`·`battle_train.js`·`jojo_index_check.js`·`policy_sim.js`·`save_probe.js` — 가 `samguk_v105.html`을 읽는다. 파일명이 v106으로 바뀌면 전부 `ENOENT`. `CLAUDE.md`·`docs/` 안의 `samguk_v105.html` 표기도 마찬가지.

## 3. 병합 방식 비교
| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. `merge --no-ff` (통합 브랜치에서) | 원래 커밋 해시 유지 — 진행표·설계 문서가 `7e93970` 같은 해시를 인용하고 있음. html 충돌 없음 | 문서 충돌 2개 손으로 해결 | **권장** |
| B. rebase로 master 위에 올림 | 일직선 기록 | 해시가 바뀌어 문서의 해시 인용이 전부 틀려짐 | 비권장 |
| C. html만 복사해 새로 커밋 | 쉬움 | 10커밋의 기록·시험기·문서 손실 | 비권장 |

## 4. 병합 순서
- **M0 보존 (완료)**: `recovered/world-expansion` 브랜치 확보.
- **M1 통합 브랜치 만들기**: master에서 `integrate/world-trade`를 따서 `recovered/world-expansion`을 `--no-ff` 병합. master는 건드리지 않음. 문서 충돌 2개 해결:
  - `코드지도.md`: 양쪽 내용을 합치고, 줄 번호는 v106 기준으로 다시 뽑는다(v106이 +668줄이라 master 쪽 표의 번호는 전부 밀림. 특히 6200대 국책·성향, 10890대 v75 이후 구간).
  - `전투_설계_v4.md`: 양쪽 수정 내용 보존(원 충돌 내용은 병합 시도 때 확인).
- **M2 이름·경로 정리**: 파일명을 `samguk_v106.html`로 확정(진행표가 이미 v106 전제). master 쪽 `tools/*.js`·`CLAUDE.md`·`docs/`의 `samguk_v105.html` → `samguk_v106.html`. 다음에 또 올릴 때 반복하지 않도록 도구들이 `samguk_v*.html` 중 가장 높은 버전을 찾는 공용 함수(`tools/_game.js` 후보)를 쓰는 안은 **선택 사항**.
- **M3 회귀 시험**: 통합 브랜치에서 `battle_sim 20`(기준선과 비교), `policy_sim`, `trade_sim`, `ship_sim`, `use_sim`, `elite_sim`을 돌려 병합 전과 비교. v106이 전투 코어에 훅 5곳(`mkUnit`·`movePts`·`dmgJ`·`hitGate`·`duelPow`)을 걸었으므로 **교역 아이템을 안 쓸 때 v105와 같은 결과**인지가 핵심 검사.
- **M4 5a 미해결 마무리**: (7) 일본도 +2, (8) AI 교역 순이익 음수(건조비·유지비를 운영 이익과 나눠 집계해 `trAiBuild` 목표 척수 6이나 `trIncl` 수량 조정), use_sim 기대값 6개 보정.
- **M5 국책과 접합**(§5) 후 `docs/국책_설계.md` §17을 v106 기준으로 갱신.
- **M6 사용자 지시**: "빌드하자" 이후에만 master에 반영. 그때 `docs/변화_*.md`에 v106 항목을 쓴다(내정·외교·인사·전투·UI 해당분) — 기존 브랜치에는 `변화_*.md` 기록이 **없다**(진행표·설계 문서가 대신함).

## 6. 위험 / 확인할 것
1. **시험 가능 범위**: `policy_sim.js`는 v105 기준. v106으로 바꿔 돌려도 교역 행동은 AI가 자동 수행하므로 병합 전후 AI 통합 속도 차이가 나올 수 있음 — M3에서 비교.
2. **AI 교역 순이익 음수(M4-8)**: 이 상태로 병합하면 교역형 AI 세력이 약해져 AI가 더 약해질 수 있음. 병합 전에 고칠지 병합 후 고칠지는 사용자 결정(권장: 통합 브랜치에서 고친 뒤 반영).
3. **5b~8 대기 단계**를 이 병합에 넣지 않는 것을 전제. 대기 단계가 나중에 들어와도 `통합 브랜치` 방식이면 충돌이 작음.
4. 사용자가 말한 "이 폴더의 v106"이 다른 곳에 따로 있으면(예: 더 최신 작업본) 그것이 `f67224a` 이후 변경을 포함하는지 먼저 확인 — 미확인.
5. 끊어진 커밋이므로 `git gc`가 돌기 전에 보존한 브랜치를 지우지 말 것.

## 7. 결정 (2026-10-20 사용자)

## JOJO_LORD 구조
`{row:72, mov:[0,48,11,56,16], atk:[528,64,12,72,0], spc:[1296,48,5,56,16], base:{병종:시작행}, fit:{병종:'foot'|'horse'|'bow'|'sage'}, remap:[col][variant]{정준색hex:결과hex}, variants:2, img:'data:image/png;base64,...'}`
- 배열 = `[x시작, 칸 가로, 칸 수, 칸 높이, 행 안 y시작]`. 이동·특수 칸 **48x56, 행 안 y=16부터**(위 8px 확장분 포함, 발은 행 맨 아래), 공격 칸 **64x72, y=0부터**.
- 22행: 보병·기병·궁병·궁기병·산악병·공성·책사 각 3행(tier 0~2), 수군 1행(noTier). `base` = 보병 0·기병 3·궁병 6·궁기병 9·산악병 12·공성 15·책사 18·수군 21. **진영색은 행에 없다**: 행 = base+tier(수군은 base). 방진은 보병 행, tier = min(2, tier+1)(기존 jojoIndex 규칙).
- 시트 색은 정준 색 한 벌(순수 빨강 램프 6톤 + 금 3톤 + 어두운 외곽 INK). `remap` 표로 진영색(col 0 아군 자주·1 우군 주황·2 적군 파랑)과 변주(variant 0 기본, 1 = 아군 보라·우군 녹·적군 청록 + **은** 표식)를 칠한다.

## 런타임 재채색 함수 (V4UI 안, `jojoImg` 옆)
```js
// (col,variant)별 한 번만 만들어 캐시. 반환: 칠한 오프스크린 캔버스(1536x1584) 또는 null(이미지 로드 전)
const LCAN = {};
function lordSheet(col, variant) {                      // col 0|1|2, variant 0|1
  const k = col * 2 + variant; if (LCAN[k]) return LCAN[k];
  const im = lordImg(); if (!im || !im.complete || !im.naturalWidth) return null;   // jojoImg 와 같은 Image 로더, src = JOJO_LORD.img
  const c = document.createElement('canvas'); c.width = im.naturalWidth; c.height = im.naturalHeight;
  const g = c.getContext('2d', { willReadFrequently: true }); g.drawImage(im, 0, 0);
  const id = g.getImageData(0, 0, c.width, c.height), d = id.data, t = JOJO_LORD.remap[col][variant], m = new Map();
  for (const h in t) m.set(parseInt(h, 16), parseInt(t[h], 16));
  for (let i = 0; i < d.length; i += 4) { if (!d[i + 3]) continue; const n = m.get(d[i] << 16 | d[i + 1] << 8 | d[i + 2]); if (n !== undefined) { d[i] = n >> 16; d[i + 1] = n >> 8 & 255; d[i + 2] = n & 255; } }
  g.putImageData(id, 0, 0); return LCAN[k] = c;
}
```
기준 구현 = `tools/gen_lord_sprites.js`의 `recolor(im, tbl)`(같은 논리, 검사기가 6벌 검증). 시트 한 장 약 9.7MB 메모리라 쓰는 (col,variant)만 만든다. 첫 호출에 한 번 getImageData 비용 발생(미측정). data: URL 이미지의 getImageData 허용 여부는 **미확인**(실제 브라우저에서 확인).

### 3. 런타임 재채색 함수

### 4. `jojoIndex` / `jojoUnit` / `unitCan` 선택 규칙
- 대상: `u.lord === true`(`mkUnit`이 이미 설정; 공성·수군 제외)이고 ① 외국 병종 분기(`J.foreign`)가 아니며 ② **`uniq`에 이름이 없거나 병종 불일치로 uniq 분기를 통과하지 못한 장수**. 즉 uniq 분기(현재 `jojoIndex` 2번째 `if (q && ...)`)가 반환하지 않은 경우에만, 마지막 `generic` 계산 직전에 들어간다. 군주라도 uniq 그림이 있는 장수(조조·유비 등)는 현행 그대로.
- `JOJO_LORD`가 있고 `JOJO_LORD.cls.indexOf(cls)`(방진은 보병 행 사용, 단계는 기존 `min(2, tier+1)`)가 유효하면 `{lord:true, row: ci*3+tier, variant}`를 쓴다. `jojoIndex`는 숫자만 반환하므로 군주는 별도 함수 `lordRow(u)`를 두고 `jojoUnit` 맨 앞에서 먼저 시도(없으면 기존 흐름). 시험용 노출은 `V4UI.lordRow`.
- `unitCan`(도트 폴백)은 군주면 머리 위에 금 2~3픽셀 관을 얹는 선택 사항(공개 배포본 대응).

### 5. 행 높이 72 반영 지점 (`jojoUnit`, 현재 14807~14822 부근)
- 군주 행: `y0 = row * 72`, 이동·특수 칸 `sw=48, sh=56`, `sy = y0 + 16`, 공격 칸 `sw=64, sh=72`, `sy = y0`. 칸 높이를 `J.row`/`sh===48` 하드코딩에서 분리해 `JOJO_LORD.mov/atk/spc`의 4·5번째 값에서 읽는다.
- 발 위치 `dy = py + TS - sh`는 그대로(위로 8px 더 그려짐). 확인 필요: 선택 테두리·깃발·위 칸 이웃과의 겹침(미확인, 14879 부근 깃발 좌표).
- 약한 프레임(`troops < max*0.25` → 이동 9·10번)·행동 끝 회색 필터(`done`)는 그대로 동작(표식도 같이 회색). 책사 행은 원본에서도 9·10번 칸이 비어 있지 않은 흰 사각형으로 보이는 경우가 있다(`lord_compare2.png` 책사 약함 칸에 해당; 원본 문제인지 미확인).
- 프레임 앵커 보정: 투구 꼭대기 `ht`는 "램프 픽셀 2개 이상인 맨 윗줄"로 프레임마다 따로 찾아(504프레임 전부 성공, 폴백 0) 표식을 얹었고, 웅크린 약함 프레임은 표식 1행 크게 + 어두운 갈색 외곽선(전 프레임)으로 가독성을 높였다. 앵커 값은 `jojo_lord.json`의 `anchors[행][프레임] = [ht, cx]`.

### 6. 폴백
`JOJO_LORD` 미정의(공개 배포)·이미지 미로드·행 없음 → `lordRow` 가 null 반환, 기존 `jojoIndex` 흐름(일반 병사 그림) → 그것도 없으면 `unitCan` 도트. 군주 전용 분기에서 예외가 나지 않도록 `try`/가드로 감싼다.

### 7. 공개 배포 시 제거 대상
`<script id="jojo-lord">`(코에이 원본 파생 도트) — `jojo-*` 정규식에 포함되지만 CLAUDE.md·`docs/README.md`의 제거 목록에 `jojo-lord`를 **추가해야 한다(미반영)**. `assets/`는 원래 커밋 대상이 아니다. 생성기·검사기 자체는 원본 데이터를 포함하지 않으므로 공개 가능.

### 8. 미확인
인게임에서의 1배·2배 가독성, 8px 확장 칸의 겹침, 두 군주 시 변주 배정 UX, 압축기 적용 시 실제 크기, `jojo_assets.py`로 `jojo-units`를 다시 만들 때 행 구성이 바뀌는지, 외국 병종 군주(전용 그림 없음, 현행 유지)의 처리.

## 3. A안 구체 설계

### 3-1 규칙
대상: `u.lord === true` 이고 ①외국 병종이 아니며 ②`uniq`에 이름이 없거나 병종 불일치로 ②를 통과하지 못한 부대.
1. cls → 풀 그룹: 기병·궁기병=`horse`, 보병·방진·산악병=`foot`, 궁병=`bow`, 책사=`sage`. (공성·수군은 lord가 아니므로 해당 없음.)
2. 풀(`LORD_ART`)은 **uniq 이름의 목록**으로 정의 → 행 번호는 `J.uniq[이름].s`에서 읽어 번호 중복 정의를 피한다. 행이 `J.rows`에 없으면 그 항목을 건너뛴다.
3. 선택: `h = 해시(u.gen)`로 풀 안의 시작 위치를 정하고, 그 이름이 이 전투에 이미 나온 uniq 장수(양 진영 모두, 조조·유비 등)이거나 이미 다른 군주가 가져간 행이면 다음 칸으로 넘긴다(순환). 같은 해시면 같은 그림 → 이름만 같으면 판마다 일관.
4. 단계: `tri`면 `s + u.tier`, 아니면 `s`.
5. 풀이 전부 막히면(드묾) 현행 `generic` 경로로 폴백. 군주가 아닌 장수·기존 uniq 장수는 **분기 자체를 타지 않아 현행 그대로.**
6. 두 군주 겹침 방지: 전투 시작 후 첫 호출 때 `W.units`의 군주 부대를 id 오름차순으로 한꺼번에 배정해 `WeakMap(W → {unitId: 행})`에 보관. 렌더 순서에 의존하지 않는다.

### 3-2 병종별 풀 (재사용 후보와 개수)

| 그룹 | 풀(권장 순서) | 개수 | 비고 |
|---|---|---|---|
| horse(기병·궁기병) | 하후돈(tri), 장료(tri), 조운, 관우, 장비, 여포, 사마의(tri) | 7 | 충분. tri 3개는 단계가 그림에 반영됨 |
| foot(보병·방진·산악병) | 허저, 전위, 주유, 육손 (+ any 풀) | 4 | 초선·축융은 제외(미확인) |
| sage(책사) | 제갈량, 몽매 (+ any 풀) | 2 | 제갈량은 동시 출전 가능성 높아 막히면 몽매→any |
| bow(궁병) | **전용 없음** → any 풀만 | 0 (+any) | 부족 |
| any(모든 그룹의 보충) | 원소 135, 유비 144, 손씨 128, 조조(tri) | 4 | 역사 군주라 군주 그림답지만, 같은 전투에 본인이 있으면 건너뜀 |

**부족 병종: 궁병.** 대안 ① any 풀(원소·유비·손씨; 조조는 마지막 순위) ② 병종 일치 없이도 군주풍으로 보이게 `generic[궁병]` 그림의 단계를 +1(방진이 이미 쓰는 `min(2, tier+1)`와 같은 방식, 색 구분 유지) ③ 새 그림 제작(자산 외부 작업, 이번 범위 밖). 권장은 ①+②: 막히면 ②. **책사**도 단독으로는 2종뿐이라 any 보충이 필요하다.

주의: any 풀의 손권·손견·손책은 한 행(128)을 공유하므로 풀에서는 "손씨" 1칸으로 센다.

### 3-3 장수급 확장(별도 옵션, 이번엔 안 함)
군주가 아닌 고능력 장수(레벨 상위, 무력/지력 90+)에게도 같은 풀을 쓰는 확장은 가능하나 같은 그림이 전장에 늘어 역사 장수와 혼동이 커지고 풀이 작아 충돌이 잦다. 사용자 지시(군주 한정)대로 현행 유지.

## 4. 구현

### 4-1 수정할 곳 (게임 html, 빌드 때)
- `jojoIndex`(14807~14816): ② 다음, ③ 앞에 군주 분기 한 줄 삽입.
- `JFIT` 아래(14806 뒤)에 새 상수 `LORD_ART`와 보조 함수 `lordArt(u)` 추가. 다른 파일(`jojo-units` 블록)은 건드리지 않음 → 공개 배포 시 블록만 지우면 되고 새 코드는 `typeof JOJO_UNITS` 가드 안에서만 실행.
- 선택: `unitCan`(14833)에 도트 군주 표식.

### 4-2 코드 스케치(의사코드)
```js
const LORD_ART = { horse: ['하후돈','장료','조운','관우','장비','여포','사마의'], foot: ['허저','전위','주유','육손'],
  sage: ['제갈량','몽매'], bow: [], any: ['원소','유비','손권','조조'] };
const LORD_GRP = { 기병:'horse', 궁기병:'horse', 보병:'foot', 방진:'foot', 산악병:'foot', 궁병:'bow', 책사:'sage' };
const LART = new WeakMap(); // V4.W -> {unitId: 행}
function lordArt(u) { const W = V4.W, J = JOJO_UNITS; let m = LART.get(W); if (!m) LART.set(W, m = {});
  if (m[u.id] === undefined) { // 이 전투 군주를 id순으로 일괄 배정
    const used = new Set(W.units.filter(x => x.gen && J.uniq[x.gen]).map(x => J.uniq[x.gen].s));
    for (const x of W.units.filter(x => x.lord && !(x.eliteName && J.foreign && J.foreign[x.eliteName] != null)).sort((a, b) => a.id - b.id)) {
      const names = (LORD_ART[LORD_GRP[x.cls]] || []).concat(LORD_ART.any).filter(n => J.uniq[n] && J.rows[String(J.uniq[n].s)] != null);
      let h = 0; for (const c of String(x.gen)) h = (h * 31 + c.charCodeAt(0)) >>> 0;
      m[x.id] = null; for (let k = 0; k < names.length; k++) { const q = J.uniq[names[(h % names.length + k) % names.length]]; if (!used.has(q.s)) { used.add(q.s); m[x.id] = q; break; } }
    } if (m[u.id] === undefined) m[u.id] = null; }
  return m[u.id] ? m[u.id].s + (m[u.id].tri ? u.tier : 0) : null; }
// jojoIndex ② 뒤: if (u.lord) { const r = lordArt(u); if (r != null) return r; }
```
(실제 구현 때 풀 순서를 "그룹 풀 우선, 이어서 any"로 하되 `h % names.length`가 그룹/any 경계를 넘지 않도록 두 단계로 나눌 것. 위는 개념 스케치.) `q`가 uniq에서 이미 `used`에 든 장수(실제 출전 중인 조조 등)는 자동으로 건너뛰므로, 풀 이름에 본인이 있어도 충돌 없음. 조건 ②에서 `u.gen`이 uniq에 있고 병종이 맞아 이미 그림을 받는 군주(조조 등)는 이 분기에 닿지 않는다.

### 4-3 저장 호환
- 그림 행은 부대·장수 필드에 저장하지 않고 렌더 때 `jojoIndex`가 계산한다. `LART`는 모듈 내부 WeakMap이라 `saveStr`(6581, 9650)의 JSON에 안 들어간다. 장수 데이터(`S.gen`)·세이브 형식 변경 없음 → 기존 세이브 그대로 열림, 같은 신무장은 불러온 뒤에도 이름 해시로 같은 그림.
- 단 `u.lord`/`u.tier`가 전투 도중 저장되는지는 **미확인**(전투 중 저장 경로 `V4.W` 직렬화 여부를 이번에 확인하지 않음). 저장되더라도 필드 추가가 없어 문제 없을 것으로 보이나 불러오기 후 `u.lord`가 살아 있는지는 확인 필요.
- 군주 교체(계승)로 `isRuler`가 바뀌면 다음 전투부터 새 군주가 군주 그림을 받는다. 이름 해시라 계승자의 그림은 달라진다(자연스러움).

## 5. 미확인 / 한계
